## Step 1: 品质决定 (ChallengeRating → Rarity)（F7验证 + ISIL确认）

场景/区域的ChallengeRating(1-5)查表得品质权重，加权随机：

| CR | Common | Rare  | Epic   | Legendary |
|----|--------|-------|--------|-----------|
| 1  | 75%    | 25%   | 0%     | 0%        |
| 2  | 65%    | 35%   | 0%     | 0%        |
| 3  | 40%    | 55%   | 5%     | 0%        |
| 4  | 30%    | 57%   | 10.5%  | 2.5%      |
| 5  | 20%    | 45%   | 20%    | 5%        |

**规律**: CR越高，高品质概率越大。CR1-2不出Epic/Legendary，CR5仍有17%概率出Common。

### forcedRarity机制（ISIL确认）

`Generate`方法接受`Nullable<ItemRarity> forcedRarity`参数。若`forcedRarity.HasValue=true`，跳过RollItemRarity直接使用指定品质。

- ISIL行5822: `CheckEqual v1179, v1168.m_value, forcedRarity` — 检查HasValue
- ISIL行5921: `Call ItemGenerator.RollItemRarity, forcedRarity @ stack_18` — 传递到Roll
- RollItemRarity内部：若forcedRarity有值，直接返回，不进行权重计算

**注意**: forcedRarity仍受ExcludedRarities限制（CanSpawnAtRarity检查在Roll之后执行）。

## Step 5: 基础模块品质决定（ISIL第7176行确认）

**核心发现**: 基础模块品质**直接绑定物品品质**，非独立Roll。

ISIL第7176行：`baseModules`变量类型为`Nullable<ItemRarity>`，其值直接取自物品品质(itemRarity)，不经过权重表Roll。

- Common物品 → 基础模块品质=Common
- Rare物品 → 基础模块品质=Rare
- Epic物品 → 基础模块品质=Epic
- Legendary物品 → 基础模块品质=Legendary

**关键推论**: Legendary物品的基础模块品质必定为Legendary，不受m_MinRarity/m_MaxRarity约束。这解释了为什么辅助发电机(Legendary品质)会出现Legendary基础模块。

## Step 6: 附加模块品质Roll + 内联过滤（ISIL第7423-7551行确认）

### 品质Roll

ISIL第7423行：附加模块品质通过`WeightedRandom`从`ModuleRarityWeights`表独立Roll，返回`ValueTuple<ItemRarity, Single>`。

权重表由物品品质决定（GetModuleWeightsForItem）：
- itemRarity=1(Common) → m_CommonItemModuleWeights(0x18)
- itemRarity=2(Rare) → m_RareItemModuleWeights(0x28)
- itemRarity=3(Epic) → m_EpicItemModuleWeights(0x38)
- itemRarity=4(Legendary) → m_LegendaryItemModuleWeights(0x48)

每个权重表包含4个float(Common/Rare/Epic/Legendary权重)，通过GetModuleWeight按moduleRarity取值：
- moduleRarity=1 → CommonWeight(0x0)
- moduleRarity=2 → RareWeight(0x4)
- moduleRarity=3 → EpicWeight(0x8)
- moduleRarity=4 → LegendaryWeight(0xC)

**默认模块权重（原版数据）**:
- Common物品: Common=100, Rare=0, Epic=0, Legendary=0
- Rare物品: Common=80, Rare=20, Epic=0, Legendary=0
- Epic物品: Common=40, Rare=30, Epic=20, Legendary=0
- Legendary物品: Common=5, Rare=10, Epic=20, Legendary=13

**关键设计**: 权重表设计使得"附加模块品质不高于物品品质"——Common物品的Rare/Epic/Legendary权重=0，Rare物品的Epic/Legendary权重=0，以此类推。这是通过权重表设计实现的非硬编码约束。

### 内联m_MinRarity/m_MaxRarity过滤（ISIL第7536-7551行确认）

Roll品质后，在模块选择循环中**内联检查**每个候选模块的m_MinRarity/m_MaxRarity：

- ISIL第7536行：`CheckLess rolled_rarity vs [module+0x70](m_MinRarity)` → 如果rolled_rarity < m_MinRarity，跳过该模块
- ISIL第7551行：`CheckGreater rolled_rarity vs [module+0x74](m_MaxRarity)` → 如果rolled_rarity > m_MaxRarity，跳过该模块

**⚠️ 重要纠正**: 之前结论"m_MaxRarity不约束运行时Generate流程"**错误**。ISIL逆向确认m_MinRarity/m_MaxRarity在模块选择循环中内联检查，是运行时过滤的关键机制。

**过滤逻辑**: 只有当 `m_MinRarity ≤ rolled_rarity ≤ m_MaxRarity` 时，该模块才被加入候选列表。

### 模块选择流程（ISIL第7651-7681行确认）

1. Roll品质 → 得到rolled_rarity
2. 遍历当前School的模块池
3. 对每个模块内联检查：m_MinRarity ≤ rolled_rarity ≤ m_MaxRarity
4. 通过检查的模块加入候选列表
5. ISIL第7651行：`WeightedRandom`从候选列表选具体模块
6. ISIL第7681行：`HashSet.AddIfNotPresent`去重检查

### 无重试机制（原版行为）

选定品质后若无可用模块（候选列表为空或全部已选），**不再二次Roll品质**，直接跳过该槽位。这导致Legendary物品可能出现2+2（2基础+2附加）而非2+3的情况。

## Step 7: 2+2现象根因（ISIL逆向确认）

**现象**: Legendary采矿激光器等物品出现2基础+2附加模块（预期2+3）

**根因链**:
1. 权重1:5:25:125下，Legendary模块概率极高(~80%)
2. 3个附加模块槽位大概率全Roll Legendary品质
3. Legendary品质模块池有限（多数模块MaxRarity≤Epic）
4. HashSet去重：已选模块不可重复
5. 无重试机制：选定Legendary品质后，池耗尽不降级重试
6. 第3个槽位无法找到新的Legendary模块 → 跳过 → 2+2

**关键模块可用性数据**（MaxRarity≤Epic的模块在Legendary Roll时被过滤）：
- PowerAmplifier(Epic), QuickReload(Epic), BonusDamage(Epic)
- ElectricCalibration_Ship(Common), BasicRounds(Common)
- 仅Legendary可用的模块：ChainLink_Ship, RailgunDoubleShot, Contagion, Virulence, CritBoost, Overwhelm_Ship

## Step 8: School模块选取（ISIL逆向确认）

从选中School的Entries中按EntryWeight加权随机选取GetModuleCount个模块（不重复）。

### 模块选择权重(GetWeight)

1. 如果schoolWeights字典存在且包含该模块 → 从字典取权重
2. 否则 → 使用mod.m_Weight（0x78）
3. 如果hasPickedInstigator=true且mod.m_IsInstigator(0x7C)=true → 乘以itemSchool.m_PostFirstInstigatorWeightScale

**注意**: m_IsInstigator标志决定模块是否受instigator缩放影响。

### 模块互斥与去重机制（ISIL逆向确认）

模块选择循环使用 `HashSet<string>` 跟踪已选模块，以 `m_AssetGUID`(0x58) 作为唯一标识：

1. 创建空的 `HashSet<string>` 和 `List<GeneratedModule>`
2. 循环条件：`List<GeneratedModule>.Count < 目标模块数`
3. 每次迭代：
   - 从模块池中 WeightedRandom 选择一个模块
   - `HashSet.Contains(module.m_AssetGUID)` → 如果已存在，跳过该模块
   - 检查模块CR范围（`m_MinRarity ≤ itemRarity ≤ m_MaxRarity`）
   - 通过检查后：`HashSet.AddIfNotPresent(module.m_AssetGUID)` + `List.Add(module)`
4. 循环退出条件：
   - **正常退出**：`List<GeneratedModule>.Count >= 目标模块数`
   - **池耗尽退出**：WeightedRandom返回的索引超出数组范围 → 直接退出（模块不足时提前结束）
   - **空池退出**：模块池为空(null检查) → 跳到错误处理

**关键发现：没有重试上限！** 循环不限制重试次数，仅靠模块池耗尽退出。当所有合法模块都已被选（HashSet已包含所有GUID）或模块池本身不足时，循环自然终止，**生成的模块数可能少于目标数量**。

**这解释了Reactor/MissileTurret少模块现象**：不是重试上限，而是模块池在CR过滤+去重后不足以填满目标数量。

### 关键过滤：模块MinRarity/MaxRarity（F9数据验证）

模块的MinRarity/MaxRarity必须包含物品品质，否则该模块不可选。

## 关键发现（F7-F11数据验证 + ISIL深度逆向确认）

1. **基础模块品质直接绑定物品品质**（ISIL第7176行确认）：baseModules类型为Nullable<ItemRarity>，值直接取自itemRarity，不经过权重表Roll
2. **附加模块品质由权重表独立Roll**（ISIL第7423行确认）：WeightedRandom返回ValueTuple<ItemRarity, Single>，受m_MinRarity/m_MaxRarity内联过滤
3. **m_MinRarity/m_MaxRarity在模块选择循环中内联检查**（ISIL第7536-7551行确认）：之前"不约束运行时Generate流程"结论**错误**
4. **附加模块品质不高于物品品质**：通过权重表设计实现（高于物品品质的权重=0），非硬编码约束
5. **2+2现象根因**：Legendary附加模块大概率Roll Legendary品质 → 多数模块MaxRarity≤Epic被内联过滤 → 候选不足 + HashSet去重 + 无重试机制 → 池耗尽 → 跳过槽位
6. **ClampModuleRarity不存在于ISIL**：ISIL全局搜索0结果，ItemSpawner中的实现应移除
7. **Weight=0的模块有44个**（F9验证），但在School Entries中多数仍有EntryWeight → 可自然生成。真正不可生成的仅PowerProtector和MinigunAffinity_Ship
8. **所有14个School的CR范围均为[-1,-1]**（F10验证）→ CR过滤在当前版本不排除任何School
9. **SelectionWeight=0.00的School存在**（F10验证）：Jonathann(Item, Entries=17)权重为0 → 永远不会被选中
10. **School #3（Jonathannn, Component, SW=0.80）排除0个组件**（F10验证）→ 所有组件类型均可通过此School获取模块
11. **模块去重使用m_AssetGUID(0x58)**（ISIL确认）：HashSet<string>去重，无重试上限
12. **PostFirstInstigatorScale**（F10验证）：Item目标School=0.05，Component目标School=0.03

### 规则13: 组件/武器品质上限（ExcludedRarities，v1.7.0验证）

组件/武器模板自身**无MinRarity/MaxRarity字段**，品质上限由BaseModuleSet.m_ExcludedRarities决定。

**ExcludedRarities机制**：
- 类型：ItemRarityFlags位标志（None=0/Common=1/Rare=2/Epic=4/Legendary=8）
- 检查：CanSpawnAtRarity → `(ExcludedRarities & (1 << rarity)) == 0`
- 降级：ApplyRarityExclusions → 被排除时向下/向上寻找最近可用品质

**实际数据（v1.7.0导出）**：

| 最高品质 | 组件 | ExcludedRarities | 模块槽位 |
|---------|------|-----------------|---------|
| **Common** | Sensor_1/2/3 | Rare, Epic, Legendary | 无(PickCount=0) |
| **Common** | SpecialWeapon_Shield_1 | Rare, Epic, Legendary | 无(PickCount=0) |
| **Common** | SpecialWeapon_TargetingModule_1 | Rare, Epic, Legendary | 无(PickCount=0) |
| **Epic** | ShieldGenerator_1/2/3 | Legendary | 有(PickCount=2) |
| **Legendary** | 其余全部组件+武器 | None | 有 |

**关键结论**：
- ShieldGenerator是**唯一有模块系统但被排除Legendary的组件**，最高Epic
- Sensor/护盾/瞄准模块连Rare都不可能，且无模块槽位
- 所有武器模板ExcludedRarities=None，理论上均可达Legendary

**品质上限完整决定因素（优先级从高到低）**：

1. **ExcludedRarities（硬限制）**：模板级品质排除，flag设置=不可能
2. **ChallengeRating权重（硬限制）**：CR1-2最高Rare，CR3最高Epic，CR4-5可出Legendary（权重0=不可能）
3. **模块MaxRarity（软限制）**：影响附加模块品质但不限制组件品质本身
4. **School模块池+Allowed/Forbidden（软限制）**：影响"全卓越"可能性

### 规则14: 模块MinRarity/MaxRarity约束机制（ISIL逆向确认，重大纠正）

**⚠️ 重大纠正**: 之前结论"m_MaxRarity不约束运行时Generate流程"**错误**。ISIL第7536-7551行确认m_MinRarity/m_MaxRarity在模块选择循环中**内联检查**。

**实际机制**:
1. **基础模块**: 品质直接绑定物品品质，**不受m_MinRarity/m_MaxRarity约束**
2. **附加模块**: Roll品质后，遍历候选模块时内联检查：
   - ISIL第7536行：`rolled_rarity < m_MinRarity(0x70)` → 跳过
   - ISIL第7551行：`rolled_rarity > m_MaxRarity(0x74)` → 跳过
   - 只有 `m_MinRarity ≤ rolled_rarity ≤ m_MaxRarity` 的模块才加入候选列表

**ClampModuleRarity不存在**: ISIL全局搜索0结果。ItemSpawner中的ClampModuleRarity实现是错误的，应移除。

**2+2现象根因**: Legendary物品附加模块大概率Roll Legendary品质，但多数模块MaxRarity≤Epic → 被内联过滤 → 候选不足 + HashSet去重 + 无重试机制 → 池耗尽 → 跳过槽位 → 2+2

### 规则15: 运行时初始化机制（ISIL验证）

ItemGenerator.Generate生成`GeneratedItem`结构体后，运行时通过`ItemModule.Initialize`完成模块初始化：

**GeneratedModule结构体**（ISIL确认）：
| 字段 | 偏移 | 类型 | 说明 |
|------|------|------|------|
| m_ModuleGuid | 0x00 | string | 模块模板GUID |
| m_UpgradeLevel | 0x08 | int | 升级等级 |
| m_Rarity | 0x0C | ItemRarity | 模块品质 |
| m_BaseValueRolls | 0x10 | Single[] | 基础值随机数组 |

**Initialize方法签名**（ISIL确认）：
```
ItemModule.Initialize(string templateGUID, ItemRarity rarity, int upgradeLevel, PersistentPickupable persistentItem, Single[] baseValueRolls = null)
```

**关键发现**：
- `baseValueRolls`参数默认null → 运行时自动生成随机值（非ItemGenerator负责）
- `RollBaseValues`方法仅存在于`Dev_ItemBuilder`（开发调试工具），**不在ItemGenerator主生成流程中**
- `GetMaxUpgradeLevel(ItemRarity)`存在于ItemModuleScriptable，按品质返回最大升级等级（Common=2, Rare=3, Epic=4, Legendary=5），但**ItemGenerator不调用此方法**——升级等级在生成时固定为0
